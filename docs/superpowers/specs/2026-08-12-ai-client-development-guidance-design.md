# MCP AI 客户端驱动的通用开发指导知识库设计

日期：2026-08-12
目标实施版本：0.1.22
状态：已根据用户审核意见修正快速开始边界，等待最终确认

## 1. 背景与目标

PKS 已接入 CodeGraph，并能针对 gardenserver 生成三类中文开发指导，但类别和项目规则仍有硬编码，尚未形成可迁移、可审核、可通过 MCP 查询并随代码增量更新的闭环。

下一功能版本只解决一个核心问题：让接入 MCP 的 AI 客户端基于 CodeGraph 事实自动发现项目功能类别，通过可打开的中文 Markdown 草稿与用户完成审核；确认后将通用的两层开发指导写入 KnowledgeStore。后续只分析变化代码及必要影响范围，不重新扫描全项目源码。

### 1.1 成功标准

- 换项目时不修改 PKS 源码，不依赖 gardenserver 或三类示例硬编码。
- 首次初始化覆盖全项目，但按模块分批向 AI 提供事实。
- 先审核功能分类目录，再生成并逐份审核开发指导。
- 待审核文档和正式阅读版均直接位于目标项目 .project-kb 根目录。
- 通过草稿 ID 和正文哈希保证入库内容等于用户审核内容。
- CodeGraph 持续维护事实；下一次 MCP AI 客户端参与时增量处理指导。
- 一级事实变化自动更新，二级指导变化和三级分类变化必须审核。

### 1.2 非目标

- 不自建 watcher、代码图或代码索引。
- 不在 PKS 内调用 ModelProvider。
- 不建设后台队列、并行调度器或通用重试平台。
- 不提供 Web 审核界面，不自动确认 AI 草稿。
- 不实现跨项目共享、向量检索或 Lua 运行时跟踪。

## 2. 职责边界

| 参与者 | 职责 | 明确不负责 |
| --- | --- | --- |
| CodeGraph | 更新代码图；提供文件、符号、调用关系、影响范围和源码证据 | 不生成方法论，不管理审核 |
| PKS | 划分批次、维护进度与快照、校验提交、渲染草稿、管理确认和 KnowledgeStore、提供 MCP | 不推断指导结论，不自建 watcher，不调用大模型 |
| MCP AI 客户端 | 分析事实、发现和归并类别、撰写两层指导、根据用户意见修改草稿、提交分级结果 | 不绕过确认直接覆盖正式指导 |
| 用户 | 打开中文 Markdown，审核、修改、确认或拒绝 | 不直接编辑数据库和内部状态 |

KnowledgeStore 是正式状态和历史版本的唯一数据源。Markdown 是用户可见的审核与阅读投影，不能绕过 MCP 状态流转成为正式数据。

## 3. 总体架构

    CodeGraph 公共接口
            ↓
    事实包与变化集边界
            ↓
    PKS MCP 工作流接口 ←→ MCP AI 客户端 ←→ 用户审核
            ↓                         ↑
    扫描进度、草稿状态、内容哈希      │ 可点击中文 Markdown
            ↓                         │
    KnowledgeStore ──────────────→ .project-kb 根目录投影

系统划分为五个独立组件：

1. CodeGraphGateway：封装现有公共 CLI，返回规范化事实和快照标识。
2. InitializationWorkflow：建立批次、发放批次、接收候选类别、汇总覆盖率。
3. GuidanceWorkflow：保存分类和指导草稿、校验结构、确认或拒绝草稿。
4. IncrementalWorkflow：比较快照、计算必要影响范围、接收三级更新结果。
5. GuidanceRepository：保存类别、正式指导、版本、进度、快照和变化集，并确定性渲染 Markdown。

组件通过结构化对象通信，不依赖具体 AI 客户端，也不判断项目名称。

## 4. 首次初始化

### 4.1 全项目覆盖、分层分批

“全项目扫描”表示所有符合 CodeGraph 项目范围的源码进入覆盖统计，不表示一次读取全部源码。PKS 先读取 CodeGraph 文件和结构元数据，再按目录、模块和依赖边界生成稳定批次。AI 每次通过 MCP 取得一个批次的结构、符号、关系及按需源码证据。

    未开始 → 扫描中 → 分类目录待审核 → 分类已确认
           → 指导生成中 → 指导待审核 → 初始化完成

每个批次仅记录批次 ID、稳定顺序、覆盖目录和文件、CodeGraph 快照、AI 提交状态、候选类别、失败原因及未覆盖文件。

中断时重新校验快照。快照未变化则从首个未完成批次继续；快照变化则把受影响批次重新标记为待分析。本版本不实现并行批次、租约、后台重试和任务优先级。

### 4.2 两阶段审核

第一阶段审核分类：

1. AI 逐批提交候选类别。
2. 全部批次完成后，AI 跨批次去重、合并、拆分和整理边界。
3. PKS 生成 .project-kb/功能分类目录-待审核.md。
4. 用户打开文档审核，AI 根据意见更新同一草稿。
5. 用户明确确认后类别目录生效。

第二阶段审核指导：

1. AI 按已确认类别逐类取得事实包。
2. AI 分别生成轻量方法论草稿和项目事实指导草稿，二者独立审核、独立版本化。
3. PKS 生成 `.project-kb/<类别名称>-方法论-待审核.md` 与 `.project-kb/<类别名称>-项目事实指导-待审核.md`。
4. 每项资产单独修改、确认或拒绝；确认一项不会隐式确认另一项。
5. 确认后分别写入 KnowledgeStore，并生成对应的正式 Markdown 投影。

分类未确认前不得生成可确认的正式指导。部分批次失败时必须显示覆盖率和未覆盖范围，不能声明全项目分类完成。

## 5. 类别与指导模型

功能类别是一类可重复开发任务的抽象，不是具体业务功能名称。它包含稳定 category_id、中文名称、用途、适用和不适用范围、代表样本、类别关系、CodeGraph 证据、置信度、未确认事项、状态和快照。展示名称可以修改，但稳定 ID 不变；合并、拆分和删除保留历史关系。

方法论与项目事实指导是两类独立知识资产，不在同一 Markdown 中拼接：

| 章节 | 内容要求 |
| --- | --- |
| 基本信息 | 类别、用途、适用和不适用范围、状态、版本 |
| 轻量方法论 | 当前范围、首次对齐问题、起步检查和待用户二次对齐事项；初版保持简单，由用户沟通后逐步完善 |
| 当前项目事实指导 | 方法论知识 ID 引用，以及入口、目录、调用链、注册、数据和配置、实施步骤、测试、发布和回滚 |
| 变体处理 | 同类功能的不同实现路径及选择条件 |
| 代码证据 | 文件、符号、调用关系、快照和必要源码锚点 |
| 未确认事项 | 无法由事实证明或仍需业务判断的内容 |
| 更新记录 | 变化集、更新级别和相对上一正式版的差异 |

项目事实指导必须回答新建同类功能从哪里开始、修改哪些文件、如何接入调用链、数据放在哪里、遵守哪些不变量、如何选择样本、如何测试发布和回滚。只罗列文件不算有效指导。项目代码变化只触发项目事实指导更新；方法论必须通过独立草稿和用户对齐更新。

## 6. MCP 工作流接口

保留现有 knowledge_status、knowledge_context、knowledge_search、knowledge_get 和 knowledge_impact，增加：

| 接口 | 用途 |
| --- | --- |
| knowledge_initialization_start | 建立或恢复初始化，冻结本轮快照并生成批次 |
| knowledge_initialization_next | 返回下一个待分析批次、覆盖信息和事实包 |
| knowledge_initialization_submit | 幂等提交候选类别和证据 |
| knowledge_draft_save | 保存分类目录或指导并渲染中文草稿 |
| knowledge_draft_confirm | 使用草稿 ID 和正文哈希确认审核版本 |
| knowledge_changes | 返回变化代码、必要影响范围和相关指导 |
| knowledge_update_submit | 提交分级结果，执行一级更新或生成二、三级草稿 |

写入接口返回绝对文件路径、草稿 ID、内容哈希、状态、下一步允许操作以及失败时未写入的内容。接口接收结构化结果，不允许 AI 直接写数据库。

确认接口重新读取磁盘草稿并计算正文哈希。机器状态字段不参与正文哈希；正文修改会使旧确认失效。确认后不得再次调用 AI 重新生成正文。

## 7. 文件与存储

新工作流不创建新子目录，新文件直接位于 .project-kb 根目录：

| 文件 | 生命周期 |
| --- | --- |
| 功能分类目录-待审核.md | 分类确认前存在，确认后删除 |
| 功能分类目录.md | 从已确认分类确定性渲染 |
| <类别名称>-方法论-待审核.md | 可迁移方法论等待审核时存在 |
| <类别名称>-方法论.md | 从当前正式方法论版本确定性渲染 |
| <类别名称>-项目事实指导-待审核.md | 当前项目事实指导等待审核时存在 |
| <类别名称>-项目事实指导.md | 从当前正式项目事实指导版本确定性渲染 |

KnowledgeStore 保存批次、快照、变化集、类别、正式指导、版本、草稿元数据和审核记录。历史版本不在目录堆积。

现有 .project-kb 子目录属于兼容范围。本版本不新增对子目录的依赖，也不实施全面迁移或删除，避免扩大成存储迁移工程。

## 8. 后续增量与分级

CodeGraph 自行更新事实。PKS 不运行独立 watcher，也不在没有 AI 客户端时生成指导。下一次 MCP AI 客户端连接或执行项目任务时，knowledge_status 或 knowledge_changes 比较当前文件元数据与已处理快照，形成待处理变化集。

允许读取一次完整 CodeGraph 文件元数据清单用于哈希比较，但只把变化代码和必要影响上下文交给 AI，不重新分析全项目源码。

| 等级 | 典型变化 | 行为 |
| --- | --- | --- |
| 一级：事实变化 | 路径、行号、符号位置、证据锚点变化，开发结论不变 | 自动更新证据、快照和正式阅读版 |
| 二级：指导变化 | 步骤、接入、约束、测试、发布或回滚方法变化 | 保留正式版，生成指导待审核文档 |
| 三级：分类变化 | 新增、删除、合并、拆分、改名或边界改变 | 保留旧分类和指导，先审核分类，再生成相关指导 |

不能匹配现有类别的新代码按三级候选处理。变化集使用内容哈希幂等去重。全部处理成功后才推进快照基线；失败则保留旧基线和待处理变化。

## 9. 查询与失败安全

- 查询默认返回正式指导，不把草稿当作正式结论。
- 存在待审核修订时，返回“可能已过期”提示和草稿绝对路径。
- 初始化未完成时返回真实覆盖率、未覆盖范围和阶段。
- CodeGraph 失败、证据不足或 AI 中断时不覆盖正式指导。
- 缺少必要章节、证据无效或快照不匹配的草稿不能确认。
- 用户拒绝时记录原因；相同变化和内容不得反复提交。
- 三级变化必须先确认分类，再生成受影响指导。
- 每份指导独立确认，不提供隐式批量确认。

## 10. 测试与真实项目验证

单元测试覆盖状态流转、幂等提交、批次和恢复、正文哈希、磁盘篡改、章节校验、快照差异、增删改、变化去重、三级处理和失败回退。

通用集成测试使用小型临时项目完成初始化、分类审核、指导审核、入库、MCP 查询和代码增量闭环，不使用项目名专用路径。

gardenserver 只作为真实验收项目，不修改业务源码。AI 不预置“登录、花园、工会”等类别；用户能打开草稿判断内容；至少验证一次一级事实更新，以及一次二级修订或三级候选；后续不得重扫全项目源码。

如果 CodeGraph 不能提供稳定文件哈希，可保存轻量哈希快照，但不得扩展为自建 watcher、解析器或代码图。

## 12. 完成定义

- 成功标准全部通过自动化或真实项目验收。
- 通用实现没有 gardenserver 项目名和三类示例硬编码。
- 所有 MCP 写接口具备正向、负向和失败回退测试。
- 默认生成中文，新文件全部位于 .project-kb 根目录。
- README、下一版本计划、审计报告、CHANGELOG、版本和知识同步完成。
- python -m project_knowledge --version、全量测试和 gardenserver 验收通过。
- 交付时明确报告 generated knowledge 是否同步，以及 curated/ADR 是否需要人工复核。
